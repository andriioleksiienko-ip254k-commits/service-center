## 1. Головна сутність

**Текст для звіту.** Після перевірки результату Л 2.2 (маршрути `/services`, `/services/:serviceId`, `/requests`, `/requests/new?serviceId=`, `/requests/:requestId/edit`, `*` працюють) для завершеного CRUD-сценарію обрано **заявку на ремонт** (Request). Вона вже має список, сторінки створення й редагування та керовану форму. Послуга (`services.js`) лишається незмінним довідником: заявка посилається на неї через `serviceId`, назва не копіюється. Модель заявки: `id`, `serviceId`, `deviceType`, `brand`, `model`, `problem`, `maxCost`. Нове поле `maxCost` – погоджена клієнтом максимальна вартість ремонту; воно дає числове поле та зв'язок із ціною вибраної послуги.

**Скріншот:** не обов'язковий (можна дати `/requests` до змін).

## 2. Правила валідації

**Текст для звіту.** Правила оформлено чистою функцією `validateRequest(input, items)` у `src/domain/requestValidation.js`. Її викликають і редактор (для показу помилок), і операції провайдера (щоб виклик поза формою не обійшов перевірку). Функція повертає `{ ok: false, errors }` з помилками за назвами полів або `{ ok: true, value }` з нормалізованими значеннями (обрізані крайні пробіли, вартість як число, без `id`).

| Поле | Правило | Повідомлення |
|---|---|---|
| `id` | створює операція додавання (`req-004`, …), у формі не редагується | — |
| `serviceId` | посилання на наявну послугу каталогу | «Виберіть наявну послугу з каталогу.» |
| `deviceType` | обов'язкове, 2–50 символів після `trim()` | «Укажіть тип пристрою.» / межі |
| `brand` | обов'язкове, 2–50 символів | «Укажіть виробника.» / межі |
| `model` | необов'язкове (клієнт може не знати), до 80 символів | межа |
| `problem` | обов'язкове, 10–1000 символів після `trim()` | «Опишіть несправність.» / межі |
| `maxCost` | обов'язкове ціле число 1–100000 грн | «Укажіть погоджену максимальну вартість.» / межі |
| `maxCost` ↔ послуга | не менше ціни вибраної послуги (`price`, «Від N грн»); перевіряється лише для коректного числа | «Послуга коштує від N грн: укажіть не менше N.» |

Обґрунтування: мінімальна довжина опису не дає подати порожній або беззмістовний текст, верхні межі захищають від випадкового вставлення великих фрагментів. Верхня межа вартості захищає від помилки з зайвими нулями. Зв'язок із ціною випливає з предметної області: межа вартості нижча за мінімальну ціну послуги робить заявку нездійсненною. Тимчасова недоступність послуги показується як інформація й не блокує заявку (як у Л 2.1).

Показ помилок: текст під полем (`FormField error`), `aria-invalid="true"` і червона рамка, `aria-describedby` = підказка + помилка; над формою `role="alert"` «Виправте позначені поля.». Колір не єдиний сигнал (є текст і значок ⚠). Помилка поля з'являється після виходу з нього (`blur`) або після спроби подання й зникає одразу після виправлення, бо обчислюється з актуальних значень.

**Код:** `src/domain/requestValidation.js` (перевірка `maxCost` зі зв'язком полів).

## 3. Спільний власник колекції

**Текст для звіту.** Створено `RequestsProvider` (контекст `RequestsContext`, хук `useRequests`). Він розташований в `AppLayout` над `Outlet`, тому колекція переживає переходи між сторінками; після перезавантаження документа відновлюються початкові записи. `data/requests.js` використовується лише в ініціалізаторі `useState` (копії записів); список і редактор читають поточну колекцію з контексту. Операції синхронні, оновлюють масив незмінно через функціональний setter (`[...previous, record]`, `map`, `filter`) і повертають явний результат: `createRequest(input)` → `{ ok: true, record }` або `{ ok: false, errors }`; `updateRequest(id, input)` → `{ ok: true, record }`, `{ ok: false, errors }` або `{ ok: false, message }` для відсутнього запису; `deleteRequest(id)` → `{ ok: true }` або `{ ok: false, message }`. При відмові стан не змінюється. Ідентифікатор генерується в операції лічильником (`req-004`, `req-005`, …) і не використовується повторно після видалення; переданий ззовні `id` ігнорується. Провайдер також веде `notice` про останню прийняту операцію (показ – крок 7). Backend і сховище не додавались.

**Код:** `RequestsProvider.jsx` (функції `createRequest` і `updateRequest`), фрагмент `AppLayout.jsx` з двома провайдерами.

**Скріншот:** `/requests` після створення: новий рядок `req-004`.

Кнопка «Відновити початкові поля» та вихід запитують підтвердження лише за наявності змін. Підключення `onSave` до операцій описано в кроці 5.

## 5. Створення й редагування

**Текст для звіту.** Обидві операції використовують один редактор `RequestPage`; маршрутні сторінки передають різні початкові дані, `onSave`, `submitLabel` і дію виходу. `RequestCreatePage` перевіряє `serviceId` з URL і передає порожню чернетку та `createRequest`; `RequestEditPage` знаходить заявку в поточній колекції за `:requestId`, передає її поля як `initialDraft` і `updateRequest` (ідентифікатор не редагується). Після `ok: true` сторінка переходить до `/requests/<id>` за `result.record.id` з `replace: true`, тобто не читає ще не оновлений стан і замінює адресу поданої форми. При `ok: false` перехід не виконується, редактор показує причину, а введення залишається. Скасування нової чернетки очищує вибір і веде до каталогу, скасування редагування – до деталей запису. Ключі `new-<serviceId>` / `edit-<requestId>` створюють окремий стан редактора для кожного запису.

**Код:** `RequestCreatePage.jsx` і `RequestEditPage.jsx` (функції `handleSave`).

**Скріншоти:** форма нової заявки перед поданням; сторінка `/requests/req-004` одразу після створення.

## 6. Перегляд і видалення

**Текст для звіту.** Додано маршрут `/requests/:requestId` і сторінку `RequestDetailsPage`, яка показує збережений запис зі спільної колекції (послуга посиланням на каталог, пристрій, модель, опис, погоджена вартість), а не чернетку. Видалення доступне з деталей і зі списку через спільний хук `useDeleteRequest`: `window.confirm` називає номер заявки й послугу та попереджає про наслідок; лише після підтвердження викликається `deleteRequest(request.id)`. Запис видаляється за стабільним `id` (`filter`), а не за позицією в таблиці. Якщо запису вже немає (застарілий ідентифікатор), операція повертає `{ ok: false, message }` і нічого не видаляє. Скасування повертає `cancelled` і не змінює колекцію та не показує повідомлення. Після видалення з деталей виконується перехід до `/requests` з `replace`; адреса видаленого запису показує «Заявку не знайдено». Видалення зі списку лишає користувача в списку, подання перераховується автоматично.

**Код:** `useDeleteRequest.js`, функція `handleDelete` у `RequestDetailsPage.jsx`.

**Скріншоти:** `/requests/req-001`; діалог підтвердження видалення; `/requests` після видалення з повідомленням.

## 7. Зворотний зв'язок

**Текст для звіту.** Повідомлення про успіх формує провайдер лише в гілці прийнятої операції («Заявку req-004 створено…», «Зміни заявки … збережено…», «Заявку … видалено…»). Компонент `RequestNotice` (`role="status"`) розташовано у `RequestsLayout` між меню розділу та `Outlet`, тому повідомлення переживає перехід між сторінками розділу заявок і лишається до закриття кнопкою «Закрити повідомлення» або наступної операції. Відмова операції прибирає попереднє повідомлення про успіх, щоб не створювати враження збереження. Помилки перевірки й операції показуються у формі (`role="alert"` + текст біля полів), форма не очищується й перехід не виконується. Помилка видалення показується на сторінці списку або деталей. Біля меню розділу постійно пояснено, що локальні дані зберігаються до перезавантаження.

**Код:** `RequestNotice.jsx`, фрагмент `RequestsLayout.jsx`, гілки `setNotice` у `RequestsProvider.jsx`.

**Скріншоти:** повідомлення після збереження на деталях і те саме повідомлення в списку після переходу; форма з відмовою (повідомлення про успіх відсутнє).

## 8. Список заявок

**Текст для звіту.** Хук `useRequestFilters(requests, items)` читає параметри зі URL `/requests`: `q` – пошук без урахування регістру в номері, назві послуги, типі пристрою, виробнику, моделі й описі; `service` – фільтр за послугою каталогу (предметна ознака заявки); `sort` – `service` (за назвою послуги, за замовчуванням), `cost-asc`, `cost-desc` (за погодженою вартістю). Невідомі значення трактуються як «усі послуги» і порядок за назвою; значення за замовчуванням не записуються в адресу. Видимий список обчислюється з поточної колекції: спочатку `filter` (новий масив), потім `sort` цього масиву, тому спільна колекція не змінюється; при однакових значеннях додатковий порядок задає `id`, а заявки з вилученою послугою йдуть у кінці. Введення тексту використовує `replace`, вибір фільтра й порядку створює окремі записи історії, «Скинути умови» прибирає всі три параметри одним викликом. Сторінка розрізняє порожню колекцію («Заявок ще немає» з посиланням на каталог) і порожній результат («За цими умовами нічого не знайдено» з кнопкою «Показати всі заявки»). `RequestTable` отримує вже відібрані записи.

**Код:** `useRequestFilters.js` (фільтр і сортування), фрагмент `RequestsPage.jsx` з двома порожніми випадками.

**Скріншоти:** `/requests?q=hp&service=srv-003&sort=cost-desc`; порожній результат пошуку; порожня колекція після видалення всіх заявок.

- `npm run lint` – 0 warnings, 0 errors; `npm run build` – успішно; `npm run dev` – запуск.
- Частина 1: `validateRequest` у Node на граничних значеннях (порожні поля, пробіли, `0`, `1.5`, `100001`, 499 при ціні 500, 81/1000/1001 символ, неіснуючий `serviceId`, підставлений `id`); форма в Chromium (помилки після blur і submit, фокус, `aria-invalid`/`aria-describedby`, відмова за зв'язком полів зі збереженим введенням, діалоги відновлення й виходу); операції провайдера через тимчасову тестову сторінку в копії проєкту (в архів не входить).
- Частина 2, `npm run preview` + Chromium (Playwright), без помилок у консолі:
